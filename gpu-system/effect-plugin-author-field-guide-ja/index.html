    After Effects Effect Plugin開発者のための設計原則と実践ガイド¶

    ―― GPU、SmartFX、MFR、キャッシュ、そして「本当に速い」とは何か¶

    対象：C++でAfter EffectsのネイティブEffect Pluginを制作する人。本文の「所感」は、Adobe SDK 25.6に基づくSkeleton開発、実D3D12 GPUを使用した模擬AEホスト試験、After Effects Internals Guide（AEIG）の研究を通じた技術的な考察であり、Adobeの公式見解ではない。2026年10月15日時点の記録。

    1. 研究を通じて、最も強く感じたこと¶

    After Effectsのエフェクトは、単独の画像処理プログラムではない。 これは今回の研究で繰り返し確認した、最も重要な認識である。

    独立した画像処理エンジンなら、自分で画像を読み込み、GPUに転送し、好きなキューに命令を投入し、結果を返せばよい。しかし、AEのエフェクトはそうではない。入力フレームを何画素必要とするか、いつ評価するか、どの順序で依存関係を解決するか、どのメモリを保持するか、何フレームを並列にレンダリングするかは、基本的にホストであるAEの契約の上に成り立っている。

    したがって、エフェクト開発者が最適化すべき対象は、単に「速いシェーダー」ではなく、AEに無駄な仕事をさせず、AEと衝突せず、正確な結果を最短で返す一連の契約である。

    第二に、「技術名」と「最適解」は別物である。 Vulkanだから速い、CUDAだから速い、Metalだから遅い、あるいはSIMDだから古い、という判断は成立しない。画像の滞在場所、ホストが渡すGPUリソース、転送の有無、解像度、フィルター半径、同時実行フレーム数、GPUの空きVRAM、CPU負荷によって、有利な実装は変わる。WindowsのD3D12とMacのMetalを第一候補にする理由も、「それが常に最高速度だから」ではなく、ホストが提供するネイティブGPUレンダー経路を尊重できるためである。

    第三に、速さより前に、測定の意味を揃えなければならない。 GPUカーネル時間、エフェクト内の処理時間、模擬ホストのコールバック時間、AEのComposition Profilerに表示されるフレーム全体のレンダリング時間は異なる。0.2msのGPUカーネルを実装しても、ホストのレンダー時間が0.2msになる保証はない。逆にキャッシュから取得した0.1msを、未キャッシュでの高速なレンダリングと認定してもいけない。

    第四に、実験の失敗は、必ずしもプラグインの不具合とは限らない。 SDKに含まれるサンプルと自分の実装に違いがあっても、それが仕様違反とは限らない。例えばGPUデバイスデータについて、AdobeのサンプルはPF_HandleSuite1で確保したHandleを使うが、SDKヘッダーの定義は「effect owned pointer」であり、生ポインター一般を禁止しているとまでは確認できない。また、実AE 26.xの検証がWindows 10上で互換性レポートに遮られた場合、それをGPU Worldの不具合と断定するのは誤りである。実験には、仕様確認 → コンパイル → 模擬ホスト → 対応OSでの実AE → 複数ハードウェアという段階がある。

    私たちが目指すべき「完成度」とは、何でもできるという宣言ではない。何が確認済みで、何が未確認かを正確に示し、それでも開発を前に進められる構造だと考えている。

    2. まず理解すべき、AE Effect Pluginの構造¶

    ネイティブEffect Pluginは、一般にホストのSelectorに応じて処理を行う。代表的な役割は次のとおり。

    役割 主なSelector／機構 設計上の注意
    登録と機能宣言 PiPL、PF_Cmd_GLOBAL_SETUP バイナリ内PiPLとランタイムのフラグを整合させる
    UIパラメータ定義 PF_Cmd_PARAMS_SETUP IDと既定値の互換性を維持し、保存済みプロジェクトを壊さない
    入力依存関係の宣言 PF_Cmd_SMART_PRE_RENDER どの入力領域が必要か、結果の最大領域はどこかを正確に表す
    CPU画像の生成 PF_Cmd_SMART_RENDER チェックアウトされたPixel Worldを適切に読み書きする
    GPU環境の用意・破棄 PF_Cmd_GPU_DEVICE_SETUP / PF_Cmd_GPU_DEVICE_SETDOWN デバイスごとの状態、同時実行中の終了処理、所有権
    GPU画像の生成 PF_Cmd_SMART_RENDER_GPU 対応フォーマット、GPU World、同期、メモリ寿命
    並列フレーム処理 MFR、PF_OutFlag2_SUPPORTS_THREADED_RENDERING スレッド安全性を満たしてから有効化する

    選択の自由があるのは、主にこれらの契約の内側である。 AEの内部キャッシュ実装やホストのGPUスケジューラーを、通常のEffect Pluginが自由に差し替えられるわけではない。

    PiPLは飾りではない¶

    PiPLはエフェクトの名前、Match Name、バージョン、対応機能などをホストへ知らせる。手書きリソースでバージョンやフラグを固定すると、SDK更新時に不一致を起こしやすい。研究用Skeletonでは、SDK 25.6のヘッダーからAdobeのPiPLToolで生成した値と、古い手書き値に差があることを発見した。

    勧める実装：Match Nameを変更しないルールを持つ／効果名やカテゴリとは分ける／SDKのバージョンマクロを使う／Global SetupのOutFlagsとPiPLを自動試験で比較する／WindowsとmacOSで同一のPiPL定義を使う。仕様番号が古いことと「ホストが必ず拒否すること」は別の命題であり、後者は実ホストで確認する。

    3. CPU実装を「劣った予備機能」と扱わない¶

    CPU SmartFXを最初に正しく完成させることを勧める。GPUを使えないハードウェア、想定外の入力形式、小さすぎるROI、GPUメモリ不足、ユーザーの環境設定、デバイス障害などの条件では、CPU経路の存在が互換性と安定性を決める。

    開発時には、少なくとも以下の点を共有する。

    • 8/16/32bpcの差、チャンネル順序、行ピッチ。画素を width × height の連続配列だと決めつけない。
    • 32bpc浮動小数点では負値や1.0を超えるHDR値を失わない。アルファを変える意図がないなら保持する。
    • CPUのScalar実装を数値的な基準として残し、SIMD（例：AVX2）は対応命令とOSコンテキスト保存機能を確認してから有効化する。
    • 範囲外アクセス、オーバーフロー、NaN／Inf、ゼロサイズ、異常なstride、キャンセルを含めてテストする。

    CPUとGPUの意味論を一致させた上で、必要な箇所だけ各実装に最適化を施す。この順番の方が、最初から複数のバックエンドを別々に書くよりもデバッグしやすい。

    4. SmartFX：描く必要のない画素を、最初から要求しない¶

    今回の研究で、GPUカーネルの改良と同じくらい重要だと感じたのが SmartFXの依存領域（ROI）と結果矩形である。

    • result_rect は今回の要求に対して生成する有効な結果領域を表す。要求領域より小さくなりうる。
    • max_result_rect は、出力要求が全面だった場合に生成されうる最大領域を表す。現在要求されたROIの大きさによって変わってはいけない。
    • 矩形が誤っていると、AEのキャッシュ・再レンダリング・周辺画素が壊れる可能性がある。
    • 入力のチェックアウトは必要十分な範囲にとどめる。Smart RenderでOutput Worldをチェックアウトするのは、実際に必要になる遅い時点がよい。

    たとえば画素ごとに独立した色補正なら、通常は出力ROIに対応する入力だけが必要となる。半径rのブラーなら、出力の各辺にrだけ加えた入力領域が必要となる。大きな空間カーネル、回転／ワープ、時間をまたぐ参照では依存領域を別途導く。速さのために依存領域を小さく「偽装」してはいけない。

    追加の注意：SmartFXでは、PreRenderで宣言した入力のcheckout_idとSmartRenderでの画素チェックアウトが対応する。異なるIDでの重複・不一致は不正な依存関係を生む。可能な限り、入力の領域計算を副作用のない関数としてテストする。

    5. MFR：「並列対応」のフラグは性能を保証しない¶

    Multi-Frame Rendering（MFR）に対応すると、同一エフェクトの複数インスタンス／複数フレームが同時に実行される。グローバル変数、共有Scratch、GPUコマンドAllocator、キャッシュやSequence Dataを、単一スレッド前提で書いてはいけない。

    推奨する基本モデルは次のとおり。

    1. 共有してよいもの：不変なアルゴリズム設定、検証済みのPipeline State、読み取り専用の定数データ。
    2. リクエストごとに分けるもの：一時バッファ、コマンド記録状態、出力、キャンセル・エラー結果、GPU完了Fenceに紐付く状態。
    3. 管理して共有するもの：メモリ予算、上限付きコンテキストプール、計算済みデータのホスト対応キャッシュ。
    4. 行わないこと：ホストのSuiteやcheckoutを呼ぶ間、独自Mutexを保持し続ける。Adobeはこれをデッドロックの重大リスクとして説明している。

    MFRでsequence_dataを更新する設計も慎重に検討する。AdobeはCompute Cacheの利用を案内しており、PF_OutFlag2_MUTABLE_RENDER_SEQUENCE_DATA_SLOWERは互換性のための速度上不利な経路になりうる。

    同時実行数を増やせば必ず高速になるわけではない。GPUのVRAM、コマンドキューの順番待ち、GPU完了まで保持するメモリがボトルネックになる場合がある。ピーク速度と同じくらい、待機時のCPU使用率、メモリ上限、Device Setdownの完了を測ることが重要である。

    6. GPU：最初の候補はホストのネイティブ経路¶

    GPU APIそのものを目的にしない。AEの提供するGPUレンダーの枠組みと、実際に受け取るGPU Worldに合った方法を先に試す。

    プラットフォーム／条件 最初に比較する候補 重要な注意
    Windows、GPUに画像が常駐 AEが提供するDirectX／D3D12系のネイティブ経路 Worldの形式、Queue、Resource State、完了順序を実ホストで確認
    macOS AEのMetalネイティブ経路 ObjC++／MSL、Rez、バンドル、コード署名をMac実機で確認
    小さいROI、GPU転送が必要、GPU非対応 CPU Scalar／SIMD GPU Dispatchの固定費が計算量を上回りうる
    NVIDIA固有の高度な処理 ホストが提供・サポートする範囲でCUDA等を比較 GPU常駐性と共有・転送コスト込みで判断
    Vulkanを内部演算に使いたい 実AE GPU Worldの共有・同期が証明できた場合に候補化 D3D12↔Vulkanの単独デモ成功はAEでのゼロコピー証明ではない

    GPU Worldは「借り物」¶

    AEから受け取った入力・出力GPU Worldを、プラグイン所有の生涯有効なリソースだと思ってはいけない。GPUがコマンドを完了する前にホストへWorldを返したり、AllocatorをResetしたり、別フレームの出力へ再利用したりするのは危険である。

    逆に、すべての処理をむやみに同期させれば、せっかくのGPU並列性を失う。理想は、安全なリソース寿命の契約を実AEで証明した上で、必要な同期だけを行うこと。未知のリソース状態を推測してバリアを置く方法、根拠のない非同期return、完了不明のGPU命令が使うメモリの即時解放は採用しない。

    さらに、PiPLとGlobal SetupでGPU対応を宣言しただけでは、その要求を処理できるとは限らない。要求されたAPI、bitdepth、デバイス状態、GPUData、ROIが対象実装に一致するときだけGPUレンダー可能と通知する。対応できないケースをCPUへ戻す判断をホストに委ねられるよう、SmartFXのPreRenderを正しく実装する。

    7. どの画像処理を、どんなアルゴリズムで書くか¶

    性能改善は、GPU APIを変更する前に計算量とメモリ移動量を減らす方が大きい場合がある。

    処理内容 第一候補 比較・注意事項
    色補正、Invert、Gain、Clamp 1パスの画素独立演算 不要な中間画像を生成しない。演算融合、HDR／Alpha維持
    小さな近傍フィルター Direct／タイル分割 境界処理、Halo、Shared Memory利用とコストを測る
    分離可能なGaussian Blur 水平＋垂直のSeparable Pass 大きい半径では計算量を削れるが中間バッファが必要
    大きな任意カーネル、PSF、Convolution Direct／FFT／分割畳み込みを比較 FFT変換とゼロパディング、境界条件、メモリ使用量を含める
    複数段階の連続処理 可能ならFusion 数値意味論や各段階の可視化が変わらない範囲で統合
    大容量画像・VRAM不足 ROI／タイル／再計算を比較 転送、スケジューリング、最大同時フレーム数も評価

    ここでの「第一候補」は全機種での最速ランキングではない。各方式の中間画像サイズ、CPU↔GPU転送、ホストの要求領域、GPUのメモリ帯域、計算／同期時間まで含めて選択する。

    特に単純なフルフレーム演算では、命令数よりもメモリ帯域とコマンド発行の固定費が制約になりやすい。スレッド配置（16×16、256×1、64×4など）は、同じシェーダーでも違う結果になり、結果の優劣は測定ノイズに埋もれやすい。少数回の勝利ではデフォルトを変更せず、比較条件を固定して反復測定する。

    8. ベンチマークで、何を「速い」と呼ぶか¶

    測定指標を混ぜないため、少なくとも4種類の時間を分けて記録する。

    計測範囲 何を示すか 測定していないもの
    GPUカーネル時間 シェーダーの実行区間 ホスト、転送、CPU処理、UI、キャッシュ
    プラグインのコールバック時間 実装内部の処理＋同期など ほかのレイヤーやAEのフレーム全体
    模擬ホストのコールバック時間 実GPUを使う反復性の高い研究条件 実AEのスケジューラーやGPU World契約
    AE Composition ProfilerのFrame Render Time 実AEにおけるコンポジション全体のレンダリング時間 単体エフェクトだけの厳密な独立コストとは限らない

    公式Composition Profilerは、キャッシュが使用されたレイヤーの時間をアスタリスク付きで示す。未キャッシュ性能を調べる際は、隔離したテストプロジェクトでメモリ／ディスクキャッシュを消去した上で測定する。

    「1ms未満」のような厳しい目標を掲げる場合は、GPUカーネルが1ms未満という数字を転用しない。実AE、同じフレーム内容、同じROI、同じ色深度、同じキャッシュ条件で複数回記録し、p50に加えてp95、p99、最大時間、ピークRAM／VRAM、異常終了の有無を示す。私たちの研究では、比較のために未キャッシュの実AEフレーム120件以上、p95・p99・最大観測値すべて1ms未満という独自の厳格な判定を採用した。これはAdobeの標準規格ではない。

    物理的な限界もある。 例えば32bpc RGBAでは1画素16バイトなので、全画素を1回読み1回書くだけで32バイト／画素の転送になる。8Kフルフレームでは約1.06GB。理論帯域448GB/sのGPUでさえ、理想的な帯域だけでも約2.37msが下限となる条件がある。ホストの処理時間を考慮すれば、「全解像度・全処理を1ms未満」は保証できない。

    今回の調査で得た数値の正しい解釈¶

    Windowsの実RTX 2070 SUPERとコンパイルしたD3D12エフェクトで、実AdobeホストではなくSDK形式の模擬ホストを使用し、3種類のスレッド配置を180独立プロセス・各48コールバックで比較した。結果は180/180でPixelの一致が確認できた。

    4Kコールバックp95の「各プロセス値の中央値」は、16×16が約0.922ms、256×1が約0.886ms、64×4が約0.890msだった。ただし別プロセスには1ms超の値もあり、改善量は研究用に設定した安定採用条件を満たさず、16×16のデフォルトを維持した。この数字を「AEタイムラインが0.886ms」と書いてはいけない。

    実AE 26.xでの試験は、Windows 10環境が2026年版の必要OS条件を満たさず、System Compatibility Reportで止まった。これはコードの成功でも失敗でもない。macOS版のMetal／Rez／署名の実機検証も完了していない。

    9. WindowsとmacOS：どこまで同一ソースにすべきか¶

    私は、1つのGPU APIを無理に両OSの共通層として押し込むより、CPU側の契約と処理意味論を共通化し、GPU実行部を薄いネイティブAdapterとして分ける設計を勧める。

    共通化するもの：EffectMainのパラメータ意味論、数値規則、ROI依存計算、キャッシュIDと不変データ、GPU定数のレイアウト、テストベクトル、キャンセル・エラーの分類。

    分離するもの：D3D12のRootSignature／PipelineState／CommandList／Fenceと、MetalのPipelineState／CommandBuffer／Encoder／Completion、プラットフォーム固有のShaderとバンドル・コード署名。

    GPU定数を例えば「幅・高さ・入力Pitchバイト数・出力Pitchバイト数・Gain・Bias」という24バイトの契約に揃えるなら、C++・HLSL・MSLのすべてでサイズ・順序・単位を検査する。ピッチを画素数とバイト数で取り違える事故は、シェーダーそのものより見つけづらい。共通化するのは意味と契約であり、OSごとの正規の高速経路を犠牲にすることではない。

    10. 初めて作る制作者に勧める実装順序¶

    1. 公式SDKのSkeletonや簡単なEffectサンプルを、まず対応OSの実AEで読み込む。Match Name、PiPL、パラメータと初期設定が正しいことを確認する。
    2. Scalar CPUで8/16/32bpcの正しい結果を出す。異常値、アルファ、行ピッチを含む数値テストを先に作る。
    3. SmartFXの依存領域、result_rect、max_result_rect、checkout_id、チェックインを確認する。
    4. 共有メモリ・sequence_data・パラメータ取得をMFR安全にしてからスレッド対応を宣言する。
    5. CPU SIMDを独立実装し、未対応CPUでは必ず安全な経路に戻す。
    6. WindowsではホストのDirectX経路、macOSではMetal経路を追加する。GPUだけでなくCPUへのフォールバックと32bpc数値一致を確認する。
    7. 画素処理・Shaderのタイミング、コールバック時間、実AEの全フレーム時間を区別して記録する。
    8. GPU実装の速さを改善する前に、不要な入力チェックアウト、過大ROI、中間画像、同期点、毎フレーム生成される重いGPUオブジェクトを探す。
    9. 低VRAM、MFR競合、デバイス喪失、強制キャンセル、プロジェクト保存・再読み込み、異なるGPU／ドライバーでテストする。
    10. 開発終了時は「検証済み」「実験済み」「未検証」「非対応」を記したリリース判定表を残す。速さと安定性を両方示せない候補は、製品既定値に採用しない。

    11. 配布直前に、自分へ問い直してほしいこと¶

    • エフェクトの保存済みプロジェクトが、次のバージョンでも壊れないか。
    • GPUが使えない場合や32bpcではない場合に、正しい代替経路または明確なエラーがあるか。
    • MFRの実行中にUIや別レンダーが走っても、書き換えられる共有状態はないか。
    • 必要な画素を取りこぼしたり、必要以上のフレーム・領域をAEに要求したりしていないか。
    • レンダー中のGPU Worldを、完了前に解放していないか。
    • エラー時に一度失敗した後、別フレームや別プロジェクトまで壊れないか。
    • バージョン、SDK、ホスト、OS、CPU/GPU、テスト条件、計測対象を再現可能な形で残したか。
    • 最速という言葉に、どのハードウェア、どの処理、どの測定値でという条件を添えたか。

    最後に――最適化の目的¶

    今回の調査で得た最大の教訓は、「最速のコード」を作ることと、「制作に使える最高のエフェクト」を作ることは同義ではない、ということだった。

    After Effectsを使う制作者にとって大切なのは、普段の画面で正しく表示され、タイムラインを移動しても止まらず、プロジェクトを開き直しても壊れず、MacとWindowsで期待した絵が出て、限られたマシンでも極端なメモリ負荷を起こさないことだ。その上でフレーム時間を少しでも短くする。

    私が理想とするSkeletonは、最初から1つの「絶対的な最高速GPU実装」を押し付けるものではない。AEの契約を壊さず、処理・ハードウェア・メモリ制約・ホスト環境に応じて、その都度正しい最適解を選び、根拠を提示できるSkeletonである。

    それは「After Effectsを完全に制御した」という意味ではなく、AEでプラグインを作るときの不確実性を、検証可能な設計へ変えていくという意味である。
